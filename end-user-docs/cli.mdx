# CLI

The `workforce` command-line tool lets you control AI agents. You can run tasks, chat interactively, manage agent configurations, schedule automated jobs, handle secrets, connect remote nodes, and more.

## Core Commands

### `workforce run`

Run a single task with an agent.

```sh
workforce run "Summarize the main points from the team meeting notes"
```

Options:
- `--agent <id>` — Which agent to use (default: `"default"`).
- `--provider <name>` — Choose an LLM provider (`anthropic`, `openrouter`, `grok`, `gemini` or `ollama`).
- `--workdir <path>` — Working directory for any file operations.
- `--max-rounds <N>` — Limit how many steps of tool execution the agent can take (default `20`).

### `workforce chat`

Start an interactive terminal chat session with an agent through a hub.

```sh
workforce chat --gateway ws://localhost:8091 --token <your-token>
```

Options:
- `--gateway <url>` — The WebSocket address of the Workforce hub (required; can come from the `WORKFORCE_GATEWAY_URL` environment variable).
- `--token <token>` — Authentication token (required; can come from the `WORKFORCE_GATEWAY_TOKEN` environment variable).
- `--agent <id>` — Select a specific agent for the session (default: `default`).

The chat provides a full terminal interface with real‑time streaming, file attachments, slash commands, and tab completion. See the [TUI Chat](#tui-chat) section for details.

### `workforce serve`

Start the long-running Workforce hub service.

```sh
workforce serve --config workforce.toml
```

This launches:
- The WebSocket gateway (default port `8091`) for chat clients.
- The admin API (default port `8090`).
- Skills like Slack integration.
- The scheduler for recurring jobs.
- Background tasks for knowledge maintenance.

### `workforce init`

Set up a new Workforce project.

```sh
workforce init
```

Creates:
- `workforce.toml` — Main configuration file.
- `policies/default.yaml` — Template for access‑control rules.
- `data/agents/default/` workspace with agent identity files (`SOUL.md`, `MEMORY.md`, etc.).

### `workforce mcp-serve`

Serve the Model Context Protocol (MCP) over stdin/stdout for a specific agent. This command is typically launched as a subprocess by Claude Code.

```sh
workforce mcp-serve --agent-id default --config workforce.toml
```

Options:
- `--agent-id <id>` — The agent whose tools should be exposed (required).
- `--exposed-tools <patterns>` — Comma-separated tool patterns to expose (e.g., `knowledge.*,linear.*`). If omitted, exposes all tools.
- `--preload-skills <names>` — Comma-separated skills to load from the agent's vault at startup.
- `--user-id <uuid>` — Canonical identity UUID for per‑user vault path resolution.

### `workforce status`

Show system status.

```sh
workforce status
```

Output includes NATS connection status, running agents, and registered nodes.

## Session Management

### `workforce sessions`

Show session history.

```sh
workforce sessions --history
```

Options:
- `--agent <name>` — Filter sessions by agent name.
- `--days <N>` — Show sessions from the last N days.
- `--limit <N>` — Maximum number of sessions to show (default `20`).
- `--redact` — Redact secrets stored across all sessions.
- `--dry-run` — With `--redact`, report what would change without writing.

## Scheduler Commands

Schedule recurring or one-time automated jobs.

### `workforce cron list`

View all scheduled jobs.

```sh
workforce cron list
```

### `workforce cron add`

Create a new scheduled job.

```sh
workforce cron add --name "Daily standup" --message "What are you working on today?" --cron "0 9 * * *"
```

Schedule types:
- `--cron <expr>` — Classic cron expression, e.g., `"0 9 * * *"` for 9 AM daily.
- `--in-time <duration>` — Run after a delay, e.g., `"2h"` or `"30m"`.
- `--every <seconds>` — Repeat every N seconds.

### `workforce cron remove`

Delete a scheduled job.

```sh
workforce cron remove <job-id>
```

### `workforce cron run`

Trigger a job immediately.

```sh
workforce cron run <job-id>
```

### `workforce cron history`

Show recent execution history.

```sh
workforce cron history
```

## Vault Commands

Manage encrypted secrets (API keys, tokens, etc.). These commands use the vault file in `--data-dir` (default `./data`). Add `--config workforce.toml` to use the configured vault instead, whether that is a file or Postgres, and `--agent <id>` for one agent's own vault.

### `workforce vault init`

Create a new encrypted vault.

```sh
workforce vault init --data-dir ./data
```

### `workforce vault set`

Store a secret.

```sh
workforce vault set slack.bot_token xoxb-...
```

Secrets are stored using dot notation, e.g., `slack.default.bot_token`.

### `workforce vault get`

Retrieve a secret.

```sh
workforce vault get slack.bot_token
```

### `workforce vault list`

List all secret paths.

```sh
workforce vault list
```

### `workforce vault delete`

Remove a secret.

```sh
workforce vault delete slack.bot_token
```

### `workforce vault rotate-key`

Generate a new encryption key for the vault. On a vault file, restart every hub that uses it with the new key; until then they refuse to save credentials. With `--config` on the Postgres backend, every secret is re-sealed under a new key. Add `--new-key-file <file>` to move to a new passphrase as well. While a passphrase change is still rolling out, a rotation that would lock out the other passphrase is refused: run `retire-key` first.

```sh
workforce vault rotate-key
workforce vault rotate-key --config workforce.toml --new-key-file new-key.txt
```

### `workforce vault retire-key`

After every hub runs with the new passphrase, stop the old one opening the Postgres vault.

```sh
workforce vault retire-key --config workforce.toml
```

### `workforce vault migrate`

Move every vault file into Postgres. While it runs, credentials can be read but not changed. Use `--dry-run` to check first; running it again skips vaults that are already moved. If a hub on Postgres already started a vault empty and saved secrets in it, that vault is reported as not imported and left as it is on both sides, and the command exits with an error so you can reconcile them.

```sh
workforce vault migrate --config workforce.toml --dry-run
workforce vault migrate --config workforce.toml
```

### `workforce vault export`

Move the vaults back from Postgres to files (rollback).

```sh
workforce vault export --config workforce.toml
```

### `workforce vault verify`

Compare each vault file with its Postgres copy, listing paths only, never values.

```sh
workforce vault verify --config workforce.toml
```

### `workforce vault audit`

Show who changed which secret and when, never values.

```sh
workforce vault audit --config workforce.toml --agent sarah --limit 20
```

## Skill Commands

Skills are extensions that add capabilities (e.g., Slack, Google Drive).

### `workforce skill list`

List installed skills.

```sh
workforce skill list
```

### `workforce skill install`

Install an instruction skill (a directory with a `SKILL.md`) from a git URL, adding
`#subpath=<dir>` for a skill inside a larger repository, or from a local directory.

```sh
workforce skill install https://github.com/acme/skills#subpath=hello-world
```

The skill is written to `skills/` under `--workdir`, and a hub started from that
directory picks it up when it next starts. The CLI clones with your own git setup, not a
token from the vault, and refuses a skill that is already installed. To read a private
GitHub repository with a vault token, to update an installed skill, or to make a skill
live at once, use `system.install_external_skill` in chat instead; see
[Installing skills](/docs/concepts/skills#installing-skills).

### `workforce skill init`

Create a default `config.toml` for a skill.

```sh
workforce skill init slack-integration
```

### `workforce skill search`

Search for available skills.

```sh
workforce skill search slack
```

### `workforce skill show`

Show details about a skill.

```sh
workforce skill show slack
```

### `workforce skill uninstall`

Remove a skill.

```sh
workforce skill uninstall slack
```

This removes the skill from `skills/` under `--workdir`, so a hub started from that
directory stops offering it when it next starts.

### `workforce skill catalog`

List the skills in the catalogs configured under `[[skills.catalogs]]`, marking the ones
already installed.

```sh
workforce skill catalog [--source <name>]
```

`--source` lists only the named catalog.

### `workforce skill catalog-install`

Install a skill from a catalog, or update an installed one to the catalog's version.

```sh
workforce skill catalog-install example hello-world
```

The CLI runs outside the hub, so a running hub loads the skill when it next starts. To
make it live at once, install it from the Skills page or with
`system.install_catalog_skill` instead.

## Local Agent Commands

Connect your local machine as a worker that can execute commands for agents.

### `workforce local-agent connect`

Register as a local agent with a remote hub.

```sh
workforce local-agent connect --gateway ws://localhost:8091 --token <token>
```

This allows the hub to delegate shell commands and file operations to your machine.
Use a device token paired to you: the agent acts for that person only, so only your
own conversations reach it.

To also offer the tools of an MCP server on your machine, name its streamable-HTTP
endpoint and the tools to offer. Its bearer is read from `WORKFORCE_NODE_MCP_TOKEN`
(or `--mcp-token-file`), never the command line:

```sh
WORKFORCE_NODE_MCP_TOKEN=wfr_… workforce local-agent connect --gateway wss://hub.example.com \
  --token <device-token> --id studio \
  --mcp http://127.0.0.1:8091/mcp/agents/<agent> --mcp-tools 'desk_*'
```

Your conversations on the hub see them as `node.studio.<tool>`.

## Training Commands (`workforce training`)

Load and manage training corpora. Can operate in two modes:
- **Direct mode** (default): Uses local storage and persistent memory backend (Weaviate) from your `workforce.toml`. No hub required.
- **Remote mode**: Connects to a running hub via `--gateway` flag or `[gateway]` config.

Direct mode requires `[training] enabled = true` and a persistent memory backend (Weaviate) configured in `workforce.toml`.

### `workforce training load`

Ingest a file into an agent's training corpus.

```sh
workforce training load --agent default --corpus api-docs api-spec.json
```

Options:
- `--gateway <url>` — Connect to a hub instead of using direct mode.
- `--token <token>` — Authentication token for remote hub.

Supported file formats: JSON, PDF, XLSX, ODS, TXT, MD, DOCX. The original file is saved for deduplication.

### `workforce training list`

Show corpora and their document counts for an agent.

```sh
workforce training list --agent default
```

Displays each corpus name, number of documents, total chunks, creation time, and processing status.

### `workforce training delete`

Remove a corpus and all its chunks.

```sh
workforce training delete --agent default --corpus api-docs
```

The memory store rows are orphaned and require a separate cleanup.

## Eval Commands (`workforce eval`)

Score an agent against a fixed set of questions on a running hub, as yourself. See
[Golden evals](/docs/reference/evals) for the set format, arms and how to read the scores.

### `workforce eval run`

Ask one agent every question of a set and print scores per use case.

```sh
workforce eval run --set fixtures/evals/example --agent analyst --out ./runs/analyst
```

### `workforce eval compare`

Run a set against several arms and print each one's paired difference from the first.

```sh
workforce eval compare --set ./sets/support --arms arms.toml --out ./runs/know-how
```

Options shared by `run` and `compare`:
- `--url <url>` — The hub (or `WORKFORCE_GATEWAY_URL`).
- `--token <token>` — Your own sign-in token (or `WORKFORCE_GATEWAY_TOKEN`). The owner token will not do.
- `--concurrency <N>` — Turns in flight at once (default `1`).
- `--limit <N>` — Ask only the first N questions.
- `--retry` — Ask failed questions again and grade ungraded answers again.
- `--turn-timeout-secs <N>` — The longest one turn may take (default `1800`).
- `--grader-agent <id>`, `--grader-model <name>` — Where the judge runs. One judge per run directory.
- `--allow-missing-credentials` — Run a test copy that lacks credentials its original has.
- `--keep-sessions` — Leave each turn's session on the hub instead of deleting it once its answer is recorded.

A run that stops carries on when the same command is run again. On Ctrl-C it waits for the turns in
flight; a second Ctrl-C abandons them.

### `workforce eval report`

Print a run directory's scores again without calling the hub.

```sh
workforce eval report --set ./sets/support --out ./runs/know-how
```

### `workforce eval check`

Validate a set and print each question's version.

```sh
workforce eval check --set fixtures/evals/example
```

### `workforce eval restore`

Put back the config of a test copy that a run which died left overridden, without running anything.
Needs a system admin's sign-in.

```sh
workforce eval restore --out ./runs/know-how
```

## Documentation Curator Command

Automatically draft end‑user documentation from source code.

```sh
workforce docs curate --all
```

Options:
- `--all` — Curate every page defined in `end-user-docs/docs-watch.toml`.
- `--changed-since <ref>` — Only curate pages whose source files changed since a Git reference (e.g., `main`).
- `--pages <path>…` — Curate specific page(s), e.g., `adapters/slack.mdx`.
- `--dry-run` — Show what would be curated without writing.
- `--no-pr` — Write changes locally but don't open a pull request.
- `--bundle` — Combine all updated pages into one PR (default is separate PR per page).
- `--max-pages <N>` — Limit the number of pages curated in this run (default `5`).
- `--tier <spec>` — Override the LLM tier, e.g., `openrouter:deepseek:powerful`.
- `--max-tokens <N>` — Override the maximum response token limit.
- `--allow-dirty` — Skip the check for a clean working tree.
- `--config <path>` — Path to `workforce.toml` (default: `workforce.toml`).

The curator reads source globs from `docs-watch.toml`, uses an LLM to draft each page, writes the updated MDX, runs validation (schema and link checks), and opens a pull request (unless `--no‑pr` is used).

## TUI Chat

The `workforce chat` command launches a full‑featured terminal user interface.

### Features

- **Real‑time streaming** — See responses as they are generated.
- **Markdown rendering** — Headings, code blocks, lists, tables, block quotes, and inline formatting.
- **File attachments** — Drag‑and‑drop files or use the `/attach` command.
- **Tab completion** — For slash commands, file paths, session IDs, and agent IDs.
- **Scrollable history** — Browse past messages with mouse support.
- **Session switching** — List and switch between active sessions.
- **Context window indicator** — Visual bar showing how much of the model's context is used.

### Keybindings

**Normal mode (input focus):**
- `Enter` — Send message (if not currently waiting for a response).
- `Ctrl+Enter`, `Shift+Enter`, `Option+Enter` — Insert a newline in the input.
- `Ctrl+U` — Clear the entire input line.
- `Ctrl+X` — Remove the last pending attachment.
- `Ctrl+Y` — Toggle mouse capture (enables native text selection outside the TUI).
- `Esc` while streaming — Cancel the current response.
- `Esc` — Switch to scroll mode.
- `Up`/`Down` (single‑line input) — Cycle through input history.
- `Tab` / `Shift+Tab` — Auto‑complete forward/backward.

**Scroll mode:**
- `i`, `Enter`, `Esc` — Return to input mode.
- `Up`/`k`, `Down`/`j` — Scroll up/down.
- `PageUp`/`PageDown` — Scroll by 20 lines.
- `Home` — Jump to top.
- `End` or `G` — Jump to bottom.
- `q` — Quit the application.

**Global:**
- `Ctrl+C` — Always quits.

### Slash Commands

**Local (client‑side):**
- `/quit`, `/exit`, `/q` — Exit the TUI.
- `/help`, `/h`, `/?` — Toggle the help panel.
- `/new`, `/n` — Start a new session (clears local history).
- `/sessions` — List active sessions (updates tab‑completion cache).
- `/switch <id>` — Switch to a session (supports prefix matching).
- `/agents` — List available agents.
- `/agent <id>` — Switch to a different agent (validates against cached list).
- `/attach <path>` — Attach a file from the local filesystem.
- `/mode` — Show connection info (gateway URL, agent, model, session).

**Forwarded to the gateway:**
- `/status`, `/compact`, `/context`, `/model`, `/health`, `/wake`, `/heartbeat`, `/reset`, `/select‑agent`, `/tools`.

### File Attachments

Supported file types and limits:
- **Images**: PNG, JPEG, GIF, WebP — up to 5 MB.
- **Text files**: Any extension — up to 1 MB (sent as UTF‑8).
- **Binary documents**: XLSX, XLS, ODS, PDF, DOCX, DOC, ODT, PPTX, PPT — up to 20 MB.

The attachment bar shows icons (`img`, `txt`, `doc`), filename, and size. Drag‑and‑drop works; on macOS, pasted file paths are automatically cleaned.

## Configuration

The CLI reads settings from `workforce.toml` (or a custom path via `--config`). Major sections include:

- `[hub]` — Data directory, listen addresses.
- `[llm]` — Default provider, model, and failover chains.
- `[gateway]` — WebSocket gateway settings.
- `[agents]` — Per‑agent configurations.
- `[vault]` — Encryption settings.
- `[training]` — Training corpus storage (must be enabled for `workforce training` commands).
- `[curator]` — Documentation curator settings (tier, max tokens).

Environment variables override the config:

- `ANTHROPIC_API_KEY`, `OPENROUTER_API_KEY`, `OPENAI_API_KEY`, `GEMINI_API_KEY`, etc.
- `WORKFORCE_GATEWAY_URL`, `WORKFORCE_GATEWAY_TOKEN`
- `WORKFORCE_VAULT_KEY` (optional)

Common global arguments:
- `--provider <name>` — LLM provider (default `"anthropic"`).
- `--api-key <key>` — API key (if not set via environment).
- `--workdir <path>` — Working directory for file operations (default `"."`).
- `--policy <path>` — Path to a YAML policy file.

## Getting Help

- `workforce --help` — General help and command list.
- `workforce <command> --help` — Detailed help for a specific command.
- `/help` inside the TUI chat — Interactive command list.

## Example Workflows

### Start a hub and begin chatting

```sh
# 1. Initialize a new project
workforce init

# 2. Start the hub service (runs in foreground)
workforce serve

# 3. In another terminal, connect and chat with the default agent
workforce chat --gateway ws://localhost:8091 --token $(grep auth_token workforce.toml | cut -d'"' -f2)
```

### Run a one‑off task

```sh
workforce run "Check the system status and report any issues" --workdir ./my-project
```

### Schedule a daily reminder

```sh
workforce cron add --name "Daily check" --message "Review open pull requests" --cron "0 10 * * *"
```

### Store and use secrets

```sh
# Store a Slack bot token
workforce vault set slack.default.bot_token xoxb-...

# Verify it's stored
workforce vault list | grep slack

# Use it in a Slack skill configuration
# (Reference in config as ${vault:slack.default.bot_token})
```

### Connect a local machine as a worker

```sh
# On your laptop, connect to the team's hub
workforce local-agent connect --gateway ws://team-hub.example.com:8091 --token <your-personal-token>
```

Now the hub can delegate shell commands and file operations to your machine.

### Load training data

```sh
# Ensure training is enabled in workforce.toml:
# [training]
# enabled = true
#
# Also require a persistent memory backend, e.g., Weaviate.

workforce training load --agent default --corpus api-reference api-spec.json
```
